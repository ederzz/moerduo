# 发布

所有命令都由你在仓库根目录运行，不要让用户手动执行，也**不需要用户确认**，看完计划没有问题就直接发布。发布用的是 `scripts/release.py`，它会依次：

1. 校验并构建素材，让 `miniprogram/data/` 是最新的。
2. 算出下一个 tag（v1、v2……），把 `miniprogram/config.js` 的 `ref` 改成它。
3. `git add -A` 并提交全部改动。
4. 打 tag，推送分支和 tag。
5. 检查 jsDelivr 上每份音频都能访问。

小程序上传不归这个 skill 管，用户自己在开发者工具里上传。

## 1. 看计划

```bash
python3 scripts/release.py --dry-run
```

会列出仓库、新 tag、`ref` 的变化和待提交的改动。

- **素材校验没通过**：把错误告诉用户，先修素材，不要发布。
- **待提交的改动里有不该提交的东西**：比如临时文件、密钥、很大的无关文件，停下来指出来问用户。这是唯一需要停下来问的情况。

## 2. 写提交说明

看一遍改动（`git status`、`git diff --stat`，需要时看具体 diff），写一条中文提交说明：

- 第一行简短概括，例如「新增素材：美加贸易战升级」「修复播放页加载超时」。
- 改动多时，空一行后分条列出。

## 3. 执行

```bash
python3 scripts/release.py -m "提交说明"
```

## 4. 处理结果

- **推送失败**：脚本会删掉本地 tag（提交保留在本地）。把错误告诉用户，问题解决后重新运行，tag 号不变。
- **音频访问失败**：jsDelivr 偶尔要几分钟才能拿到新 tag，告诉用户稍后再试。一直失败的话，检查仓库是不是公开的。

## 5. 汇报

- 提交说明、新 tag、推送结果。
- 每份音频能否访问。

## 规则

- 每次发布都用新 tag，不要删除、移动或复用已经推送的 tag。jsDelivr 会永久缓存 tag 下的文件，复用会让手机拿到旧音频。
- 不要强制推送（`--force`），不要改写已推送的提交。
